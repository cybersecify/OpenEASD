# Scan Modes 2×2 (Active Light + Start-Scan matrix) — Design Spec

> **Status:** Proposed. Design agreed via brainstorming: four predefined
> workflows mapped to a passive/active × light/deep matrix + Custom; Active
> light = discovery backbone + cheap checks; "deep" is the thorough superset.

**Goal:** Turn the Start-Scan page into a clear **2×2 matrix of scan modes**
(passive/active × light/deep) plus **Custom**, backed by four predefined
workflows. Three already exist; this spec adds the missing **Active Light**
workflow and restructures the Start-Scan UI so every mode is a first-class,
one-click choice with the authorization boundary shown.

**Owner:** OpenEASD core (`apps/core/engine/workflows`) + the React SPA
(`frontend/src/pages/ScanStartPage.jsx`). **Depends on:** the passive/active
classification (`is_passive_tool_set`), the predefined-workflow pattern
(migrations `0022_create_passive_scan_workflow`, `0036_create_quick_recon_workflow`),
and the runner's `naabu → service_detection` auto-injection. **Scope:** one new
workflow + drift-lock test, a UI restructure, and docs. **Additive** — no change
to Full Scan, Passive Scan, Quick Recon, the `quick_recon` flag, or any tool's
behavior.

---

## 1. Motivation

OpenEASD already draws two independent lines through its scanning:

- **passive vs active** — the authorization boundary (`is_passive_tool_set`;
  passive = no packets to the target = no `DomainAuthorization`).
- **light vs deep** — cost/scope: a fast first look vs a thorough sweep. v2.24.0
  introduced this for passive tools (Quick Recon = the apex-only four).

Crossed, these give a **2×2** of scan intents. Three cells already have a
predefined workflow; the **Active Light** cell is missing, and the Start-Scan UI
exposes only three flat presets (Passive recon / Full scan / Custom), so Quick
Recon is reachable only via a Custom → workflow dropdown and there is no fast
*authorized* mode at all. This spec fills the matrix and makes every cell a
one-click preset.

---

## 2. The matrix

| | **Light** | **Deep** | Authorization |
|---|---|---|---|
| **Passive** | **Quick Recon** — `domain_security, dns_history, hudson_rock, breach_check` *(exists)* | **Passive Scan** — all passive tools *(exists)* | none (no-auth) |
| **Active** | **Active Light** — discovery backbone + cheap checks *(NEW)* | **Full Scan** — all 30 tools *(exists, default)* | required |

Plus **Custom** (pick categories / a saved workflow) — unchanged.

**"Deep" is the thorough superset of "light"** on each axis: Passive Scan
includes the passive-light four; Full Scan includes everything in Active Light.
This matches the existing workflows, which are **unchanged**.

**The authorization boundary runs along the passive/active axis** (the matrix
rows): both passive cells need no authorization; both active cells require
`DomainAuthorization`. The depth axis never affects authorization.

---

## 3. Active Light workflow (the one new backend artifact)

**Why these tools:** a bare set of "config/exposure probes" cannot stand alone —
`httpx` reads open `Port` rows, `web_checker` reads `URL` rows (from httpx),
`tls_checker` iterates `Port` rows, and `ssh_checker` filters `Port` by
`service=ssh|22`. Only `domain_probe` is apex-standalone. So a useful active-light
mode needs the **discovery backbone** feeding the **cheap checks**; "light" vs
"deep" for active is therefore *"discovery + cheap checks" vs "+ the expensive
engines"* (nuclei templates, nmap NSE, amass, katana crawl, cloud/takeover/
js_secrets/historical_urls).

**Membership — 8 explicit `WorkflowStep`s, in pipeline-phase order:**

| Tool | Role |
|---|---|
| `subfinder` | passive subdomain discovery |
| `dnsx` | resolve to public IPs |
| `naabu` | top-100 TCP port scan |
| `httpx` | web probe on discovered host:port |
| `domain_probe` | apex active probes (AXFR / SMTP relay / MTA-STS) |
| `web_checker` | headers / cookies / CORS / security.txt |
| `tls_checker` | cert / cipher / protocol on all ports |
| `ssh_checker` | SSH config on ssh ports |

`service_detection` is **not** listed — it is `core: True` (hidden from the
workflow UI) and the runner **auto-injects it after `naabu`**, so it runs at
scan time without being a stored step.

**Properties:**
- Non-default, idempotent create + reverse delete — same shape as migration 0022.
- Migration `0037_create_active_light_workflow.py`, depends on
  `0036_create_quick_recon_workflow`.
- Contains active tools, so `is_passive_tool_set(enabled_tools())` is **False** →
  `/api/workflows/` reports `is_passive=False` → the UI requires attestation and
  the scan-start gate requires `DomainAuthorization`. No new auth code.
- **Excludes** every slow engine — that invariant is what keeps "light" light and
  is guarded by a test (§5).

---

## 4. Classification approach — curated workflows, not a new flag

"Light" means **different things on each axis**: passive-light is *apex-only, no
fan-out*; active-light *requires* discovery fan-out (subfinder/dnsx/naabu). A
single boolean cannot derive both (marking `subfinder` "light" for active-light
would wrongly pull it into `light_passive_tools()` and break Quick Recon).

Therefore the depth split is realized as **curated predefined workflows**:
- Quick Recon stays flag-derived (`light_passive_tools()`, the `quick_recon`
  flag) — **unchanged**.
- Active Light is an **explicit, curated tool list** in its migration, pinned by
  a drift-lock test (§5).
- The matrix UI maps each cell to its workflow **by name**.

The `quick_recon` flag is **not** renamed or generalized; no new tool-level flag
is added.

---

## 5. Drift lock (tests — `tests/unit/test_active_light.py`)

- **Membership:** the "Active Light" workflow's `enabled_tools()` **equals** the
  explicit set `{subfinder, dnsx, naabu, httpx, domain_probe, web_checker,
  tls_checker, ssh_checker}` (set equality — fails if a tool is added or dropped).
- **Not default; exists:** `is_default is False`.
- **Authorization preserved:** `is_passive_tool_set(enabled_tools())` is **False**
  (it contains active tools), so the active cell always requires authorization.
- **Light stays light:** the workflow contains **none** of the heavy engines —
  `nmap, nuclei, nuclei_network, katana, amass, cloud_assets, takeover_check,
  js_secrets, historical_urls, asn_discovery, asn_cluster, github_recon,
  github_secrets, shodan, tldsquatting, cve_intel` — a guard that a future edit
  can't quietly fatten the light mode.
- **Discovery present:** `naabu` ∈ members (so `service_detection` auto-injects
  and `httpx`/`tls_checker`/`ssh_checker` have ports to work on) — documents the
  dependency the composition exists to satisfy.

## 6. Start-Scan UI (`frontend/src/pages/ScanStartPage.jsx`)

Replace the three flat preset cards with a **2×2 grid + a Custom card**:

```
Scan type
┌─────────────────────┬─────────────────────┐
│ ◉ Quick Recon       │ ○ Passive Scan      │   PASSIVE
│   light · ~secs      │   deep · full sweep  │   ✓ no auth
│   N checks           │   N checks           │
├─────────────────────┼─────────────────────┤
│ ○ Active Light      │ ○ Full Scan         │   ACTIVE
│   light · fast probe │   deep · everything  │   ⚠ auth required
│   N tools            │   N tools            │
└─────────────────────┴─────────────────────┘
[ ○ Custom — pick categories or a saved workflow ]
```

- Each cell resolves to its predefined workflow **by name** (`Quick Recon` /
  `Passive Scan` / `Active Light` / `Full Scan`) and submits `workflow_id`.
- **Auth copy follows the row:** passive cells show green "✓ No authorization
  needed"; active cells show amber "⚠ Authorization required". Attestation stays
  gated by the existing `selectionIsPassive && !scheduled` logic (keyed on the
  resolved workflow's `is_passive`) — unchanged and already correct.
- **Scope line per card:** the workflow's enabled-tool count (reuse
  `enabledToolCount`).
- **Graceful fallback:** a cell whose workflow is absent (older DB without the
  Quick Recon / Active Light migration) is hidden; the grid still renders the
  cells that resolve, and `Full Scan` / `Custom` always remain.
- **Default selection:** Quick Recon (top-left — fastest, no-auth). If Quick
  Recon is absent, fall back to the first available passive cell, else Full Scan
  (preserves today's "fall back to full" behavior).
- **Custom** is unchanged (by-category / by-workflow), rendered below the grid.
- Responsive: the grid is 2-col on `sm+`, single-column stack on phone (existing
  Tailwind patterns; keep the 16px side gutter).

No change to the submit flow, the category path, scheduling, or the API payload
shape beyond selecting the right `workflow_id`.

## 8. Design invariants (guarded by tests)

- Active Light membership == the explicit 8; non-default; contains active tools
  (auth required); excludes every heavy engine; includes `naabu` (discovery).
- Quick Recon, Passive Scan, Full Scan, the `quick_recon` flag, and the
  authorization boundary are all unchanged (additive-only).
- The UI maps each matrix cell to its workflow by name and hides a cell whose
  workflow is absent (no crash on an older DB).

---

## 9. Non-goals

- Renaming or generalizing the `quick_recon` flag; adding an active-light
  tool-level flag (Active Light is curated).
- Changing the membership of Passive Scan or Full Scan.
- A scheduled/default Active Light, or any scheduler change.
- Touching `runner._LOW_MEM_PARALLEL_SAFE` (separate memory/IO axis).
- Category-view changes beyond what the grid restructure needs.
